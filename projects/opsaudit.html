OpsAudit

Finding what operations automation silently misses, and putting a price on it.

Status
Live demo
Data
Synthetic, plus one public real-data check
Built with
JavaScript, React, SQLite, Python, scikit-learn

The problem

Automated procedures watch for a condition, such as a port blocked for 30 minutes, and act on it. They run on live events with no historical replay. If the platform is down, an event arrives late, or a rule is slightly too narrow, the case is never picked up and nothing records that it was missed.

Success metrics are calculated over the cases that were handled, so a procedure can report 100% while missing a quarter of what it should have caught.

This is a demo of the kind of work I did at my TSMC internship. All data on this page is synthetic, except the clearly labeled public-data check.

Who it is for

  • Operations and program managers who own automated procedures and need to know what those procedures are not catching, what it costs, and which fix to do first.
  • Automation and process engineers who write the detection logic and maintain it as documents drift.

Key decisions and tradeoffs

Audit from raw history, not from the procedure's own log

Chose
Rebuild what each procedure should have picked up from raw events, then anti-join against what it logged.
Over
Trusting the procedure's reported success rate.
Because
The reported rate only counts handled cases, so it cannot show what was never seen.
Cost
It needs two independent sources, and in practice the hard part is access to the automation's own log.

Hand-written answer keys, with checks built to fail

Chose
Seven hand-written baseline queries as the answer key, and scorers that are themselves tested by feeding them deliberately wrong answers.
Because
A query that finds nothing looks the same as one that is broken, so the audit fails if any procedure returns zero misses.
Cost
I wrote the keys, so they share my vocabulary and the numbers lean optimistic.

Fix the control limits from a healthy baseline

Chose
Set statistical process control limits from the first 15 subgroups, then hold them fixed.
Over
Setting limits from all the data.
Because
Limits from all the data let a drift drag the center line toward itself and hide it.

Price the misses with assumptions anyone can edit

Chose
Turn each miss into labor hours and cost at risk, group misses into fixes, and rank them by cost, hours or payback. Every input is an editable assumption, set low on purpose.
Because
Managers act on a ranked list of fixes, not on a miss count.
Cost
The dollar figures are illustrative, not measured. The annualized figure just scales the 14-day window and should not be read as a forecast.

Freeze the baseline before training the model

Chose
Branching hand-written keyword rules as the baseline, frozen before any model was trained. One stratified split, tuning by cross-validation on training data only, and the test set scored once.
Because
It keeps the comparison between the model and the rules honest.

Split the AI layer into three calls

Chose
Resolve the procedure, extract the condition, then compose the SQL, as three separate model calls graded against the hand-written baselines.
Because
A wrong extraction is visible before any SQL is written, so a person can catch it. The model proposes and the baselines check it.

Results

  • 26.1%miss rate: 24 of 92 qualifying cases
  • 89% vs 66%random forest vs hand-written rules
  • 33specific check types classified

Audit. 92 qualifying cases, 68 logged, 24 missed. The largest fix, an outage backfill, covers 8 of the 24 misses.

Statistical process control. A drift planted in one lane alarmed three subgroups after it started, and the chart on the difference between the two parallel lanes flagged it at subgroup 22. A single-subgroup spike produced exactly one alert.

Classifier. On the 413-record test set, the random forest named the specific check 89.1% of the time. Hand-written rules with multilingual keywords scored 66.3%, and always guessing the most common class scored 2.9%.

Real data, and a weak result. I stress-tested the same ideas on UCI SECOM, a public semiconductor dataset of 1,567 production runs. The control charts as built did not separate failures from passes (95.0% of failing runs were flagged, but so were 98.8% of passing runs), and no classifier clearly beat chance on the later runs. I report it as it came out.

AI layers. One run each. The right procedure resolved 5 of 5 times, but only 2 of 5 generated queries matched the baseline exactly. Root-cause grouping passed 3 of 5 checks and recovered the outage cluster exactly.

Limits: synthetic data, a small sample (24 misses, one 14-day window), answer keys I wrote myself, and one run of each AI layer. Treat the numbers as a demonstration of method, not a benchmark or a forecast.

What I would do next

  • Run it on a real pair of sources, the raw events plus the automation's own log, since that access is the real bottleneck.
  • Replace my hand-written answer keys with keys written by someone who owns the procedures.
  • Repeat the AI runs enough times to report a spread, instead of one sample each.
  • Extend the same audit to other domains that have the same two-source structure, such as inventory reorders, shipment exceptions and ticket escalations.
